# Herramientas del CI, con versión fija (RED-85, Cambio 196).
#
# Hasta acá los workflows hacían `pip install ruff`, `pip install coverage`,
# `pip install pip-audit` y `pip install mkdocs-material` **sin versión**: cada corrida
# instalaba lo último publicado. Un release de cualquiera de ellas vuelve rojo un PR que
# no cambió una línea —una regla nueva de Ruff, un `fail_under` que se mide distinto, una
# advisory nueva de `pip-audit`— y el autor del PR no tiene cómo saber que el rojo no es
# suyo. El caso más caro es `pip-audit`, que desde el Cambio 121 es un check obligatorio
# del ruleset y su base de advisories cambia sola: un release suyo frena **todos** los
# merges abiertos a la vez.
#
# Pinear no es destildar el check: cuando una advisory nueva aparezca, la salida sigue
# siendo `security/excepciones.toml` con motivo, ticket y `vence_el` corto (RED-63). Lo
# que se gana es que la advisory llegue **cuando se sube el pin**, en un PR que la mira,
# y no en el medio de otro trabajo.
#
# Se instala entero (`pip install -r requirements-ci.txt`) en todos los jobs que usan
# alguna de estas herramientas, aunque cada uno use una sola: tener las versiones en un
# archivo y no repartidas por los YAML es el punto de la ficha, y el costo son ~20 s de
# descarga en jobs que duran minutos. Las versiones son las que el CI ya venía
# instalando al 09-oct-2026, así que pinearlas no cambia ningún resultado.
#
# Lo sube dependabot (`.github/dependabot.yml`, semanal, contra `development`).
#
# NO va acá nada que la aplicación importe: eso es `requirements.txt` (producción) o
# `requirements-dev.txt` (local). Los jobs que corren la suite instalan `requirements.txt`
# además de este archivo.

# `Ruff errores` (`--select F`) y `Ruff estilo` (E/W/I + `ruff format --check`), los dos
# bloqueantes. El pin es lo que permitió hacer bloqueante el segundo (pendiente del
# Cambio 320): sin él, una regla E/W nueva lo pondría en rojo sin que nadie toque nada.
# Subir esta versión es el PR donde aparecen los hallazgos nuevos: se formatea ahí.
ruff==0.17.1

# `Tests & Coverage`: `coverage run manage.py test` + `coverage report` con
# `fail_under = 79` y el piso por módulo crítico (TST-03). Un cambio en cómo mide ramas
# mueve el número sin que cambie el código.
coverage==7.16.2

# `tblib` no es una herramienta: es lo que hace que una falla bajo `--parallel` se vea.
# Django pickea el resultado de cada worker para mandarlo al proceso padre, y un
# `traceback` no es pickleable por sí solo. Sin `tblib`, su propio código avisa que
# «pickling the traceback will always fail»: la suite muere con
# `TypeError: cannot pickle 'traceback' object` **sin decir qué test falló**, el worker
# queda colgado y el job corre hasta que GitHub lo cancela por timeout —25 minutos—.
# Peor todavía, `gh pr checks` lo muestra como `cancel`, idéntico a una cancelación por
# push, así que lo primero que uno hace es relanzar, y relanzar un fallo determinista no
# lo arregla nunca.
#
# Eso es RED-88. El Cambio 163 la dio por cerrada, pero lo que arregló fueron los tests
# que fallaban: el modo de falla siguió ahí, dormido, esperando la próxima falla. Llegó
# el 12/10/2026 con los snapshots de Becas y costó media hora de diagnóstico.
# Con `tblib` instalado la misma falla sale al instante y con su traza completa.
tblib==3.2.2

# `Pip Audit`, obligatorio desde el Cambio 121.
pip-audit==2.10.1

# `Bandit Security Scan` (no bloqueante). Ya estaba pineada en el YAML desde el
# Cambio 121; se muda acá con el resto.
bandit[toml]==1.9.4

# `Docs Auto Deploy`, que publica `docs/client/` en GitHub Pages con `contents: write`.
mkdocs-material==9.7.7

# `Tipos (mypy)` (no bloqueante, RED-76). El alcance —qué módulos se verifican— vive en
# `files` de `[tool.mypy]`, en `pyproject.toml`, y crece un módulo por PR.
#
# Los tres van juntos o no van: `django-stubs[compatible-mypy]` es el que fija qué mypy
# soporta, y `djangorestframework-stubs` exige `django-stubs>=6.0.4`. La ficha proponía
# `mypy==1.14.1` + `django-stubs==5.1.3` + `djangorestframework-stubs==3.15.2`; esa terna
# es de la época de Django 5.1 y hoy ni siquiera resuelve (`pip` da `ResolutionImpossible`:
# drf-stubs 3.17 pide django-stubs 6). Estas son las versiones compatibles con el par que
# corre el CI, Django 5.2.17 + DRF 3.17.2. Las sube dependabot con el resto.
mypy==2.1.0
django-stubs[compatible-mypy]==6.1.2
djangorestframework-stubs[compatible-mypy]==3.17.0
